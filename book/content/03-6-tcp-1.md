## [3.9]{.sec}Transport: UDP, TCP, flow control and congestion control [Must · ■■■]{.tag} {#s3-9}

The network layer delivers packets from one machine to another, but it does not say which program should receive them, nor does it promise that they arrive, in order, once. The transport layer adds exactly these things. It is also the layer where interviewers spend the most time, because a TCP question can start at a header field and end at the behaviour of a data-centre fabric. This section is therefore the longest in the pillar: it covers ports, UDP, the TCP header, connection set-up and teardown, the state machine and reliability here, and flow control and congestion control in the next pages.

::: bigidea
UDP is a thin service that adds ports and a checksum to IP, while TCP builds a reliable, ordered, flow-controlled and congestion-controlled byte stream on top of an unreliable network by using sequence numbers, acknowledgements, timers and two windows.
:::

### Ports and sockets

An IP address names a machine; a *port number*, a 16-bit value, names a program on it. A *socket* is one endpoint, an address-and-port pair, and a TCP connection is identified by the four values (source IP, source port, destination IP, destination port), the *4-tuple* (with the protocol, the 5-tuple). Hence one server port such as 443 can serve millions of clients at once, because every client gives a different tuple. Ports below 1,024 are *well-known* (80 for HTTP, 443 for HTTPS, 53 for DNS, 22 for SSH; the full list is in the Revision Spread), 1,024 to 49,151 are *registered*, and 49,152 to 65,535 are *ephemeral*, picked by the operating system for the client side of a connection (Linux uses 32,768 to 60,999 by default). The sockets API that programs use is treated in Pillar 7.

### UDP

The *User Datagram Protocol* is the smallest possible transport: the 8-byte header, shown with the TCP header below, holds the two ports, a length and a checksum that covers the data and parts of the IP header. There is no connection, no retransmission, no ordering and no congestion control: a datagram is sent and may arrive, or not. That is exactly right when a late packet is worthless, or when the application has its own recovery: DNS queries (one question, one answer), voice and video calls, online games and QUIC, the modern transport that the web is moving to (Section 3.10). UDP also suits broadcast and multicast, which a connection cannot.

*Source* and *destination ports* identify the endpoints. The *sequence number* is the byte-stream position of the first data byte in the segment; the *acknowledgement number* is the next byte the sender of the acknowledgement expects, so it confirms everything before it (a *cumulative* acknowledgement). *Data offset* gives the header length in 32-bit words, since options vary. The eight flag bits are: CWR and ECE, used for explicit congestion notification; URG, nearly obsolete; ACK, set on every segment after the first SYN; PSH, a hint to deliver to the application now; RST, which aborts the connection; SYN, which synchronises sequence numbers at the start; and FIN, which ends one direction. The *window* field is the receiver's advertised free buffer in bytes (Section 3.9, flow control). The checksum covers header, data and an IP pseudo-header.

The *options* appear mostly on SYN segments: the *maximum segment size* (MSS, the largest data per segment, usually 1,460), *window scale* (a shift count that multiplies the window, needed on fast long paths), *SACK-permitted* (enables selective acknowledgements) and *timestamps* (used to measure round-trip time and to protect sequence numbers on fast links).

### Connection set-up: the three-way handshake

TCP connections have a beginning and an end, and both sides keep *state* (variables such as the next sequence number, the window and timers) while the connection lasts. The *three-way handshake* creates that state at both ends. The client sends a SYN with its *initial sequence number* (ISN); the server answers with a SYN,ACK that acknowledges the client's ISN and announces its own; the client acknowledges that in turn. The ISN is not zero but a random number: it prevents old segments of a former connection from being accepted by the new one, and it makes it hard for an attacker to guess sequence numbers and inject data (RFC 6528).

::: example
**Handshake, data and teardown with ISNs 1000 (client) and 5000 (server).**

1. SYN: seq = 1000. The SYN consumes one sequence number, so the next client byte is 1001.
2. SYN,ACK: seq = 5000, ack = 1001. The server's SYN also consumes one number.
3. ACK: seq = 1001, ack = 5001. The connection is established on both sides.
4. The client sends 500 bytes, seq = 1001, ack = 5001. The server replies with a pure ACK, seq = 5001, ack = 1501 (1,001 + 500). The pure ACK consumes no sequence number.
5. The client closes: FIN,ACK with seq = 1501. The server ACKs with ack = 1502, because the FIN counts as one byte.

[Result: SYN (1000), SYN,ACK (5000, ack 1001), ACK (1001, ack 5001); after 500 bytes the acknowledgement is 1501; the FIN advances it to 1502. A SYN and a FIN each use one sequence number; a pure ACK uses none.]{.result}
:::

[**Why three?** — A and B each need to be sure the other heard their ISN. Two messages leave one direction unconfirmed; four are not needed, because the server combines its ACK and SYN in one segment.]{.margin}Two messages would not be enough, because the server could not tell whether its own SYN,ACK had arrived, nor distinguish a fresh SYN from a delayed duplicate of an old one. The third segment confirms to the server that the client heard it, and that the request is current. If two hosts send SYNs at the same moment, a *simultaneous open*, they still end up with one connection after exchanging SYN,ACKs.

A server must remember each half-open connection, and this is exploited by a *SYN flood*: an attacker sends a stream of SYNs from forged addresses and never answers the SYN,ACKs, filling the queue of half-open connections until real clients are refused. *SYN cookies* defeat it by keeping no state: the server encodes a hash of the 4-tuple, a secret and a coarse timestamp (and a code for the MSS) in the sequence number of its SYN,ACK, and forgets the connection. A legitimate client's ACK returns that number plus one; the server verifies the hash and rebuilds the connection. Only genuine clients cost the server any memory, at the price that some options of the SYN, such as the window scale, may be lost.

The side that sends the first FIN, the *active closer*, ends in the *TIME_WAIT* state and waits for twice the *maximum segment lifetime* (2 MSL; Linux uses a fixed 60 seconds) before it forgets the connection. There are two reasons for this. If the final ACK is lost, the peer retransmits its FIN, and the active closer must still be there to acknowledge it. And any stray segments of the old connection, still wandering the network, must die before the same 4-tuple is reused, or they could be mistaken for data of the new connection.

The passive closer sits in *CLOSE_WAIT* between receiving the FIN and calling `close()`. That state lasts only as long as the application takes to notice the closed connection; a server with thousands of CLOSE_WAIT sockets therefore has a bug in its own code, which forgets to close sockets, and no network setting will cure it. TIME_WAIT, in contrast, is normal; it becomes a nuisance only on a busy client or proxy, which opens many short connections to one destination and runs out of ephemeral ports (about 28,000 ports and 60 seconds allow roughly 470 new connections per second to a single destination). The remedies are connection reuse, more source addresses or ports and, on Linux, `tcp_tw_reuse` for outgoing connections.

A TCP stack sends an *RST* (reset) when it receives a segment for which no connection exists, which includes a SYN to a port where nothing listens, so that the sender fails at once instead of timing out. An RST is also sent when an application aborts (closing a socket with unread data, or with a zero linger time), when a firewall or an intrusion-prevention box injects one to kill a flow, and when a segment violates the connection state, such as data arriving after the peer has crashed and restarted.

::: trap
*Claim:* "TIME_WAIT is on the client, and a server never has it." *Why it is wrong:* TIME_WAIT belongs to whichever side closes first, the *active closer*. *Correct statement:* a web server that closes idle connections itself accumulates TIME_WAIT sockets, while a client that closes first has them on its side; the passive closer goes through CLOSE_WAIT and LAST_ACK.
:::

### Reliability: acknowledgements, timers and fast retransmit

TCP numbers bytes, and the receiver acknowledges the next byte it wants. To avoid an acknowledgement for every segment, a receiver may delay the ACK, typically until a second full segment arrives or about 40 ms (Linux) to 200 ms (older systems) have passed. If a segment is lost, later segments arrive out of order and each one makes the receiver repeat the same acknowledgement, a *duplicate ACK*.

The sender starts a timer when it sends data. The *retransmission timeout* (RTO) must exceed the round-trip time (RTT), or packets are resent needlessly, but not by much, or recovery is slow. It is therefore computed from measured samples by the method of Jacobson and Karels (RFC 6298). With sample R, a smoothed average SRTT and a mean deviation RTTVAR, the update is RTTVAR = (1 − β) RTTVAR + β |SRTT − R|, then SRTT = (1 − α) SRTT + α R, with α = 1/8 and β = 1/4, and RTO = SRTT + 4 RTTVAR. *Karn's algorithm* adds that samples from retransmitted segments are ignored, since it is unclear which transmission the ACK answers; and after each timeout the RTO is doubled (*exponential backoff*).

::: example
**RTO update from SRTT = 100 ms and RTTVAR = 25 ms with samples 120 ms and 80 ms.**

1. First sample R = 120: |SRTT − R| = 20; RTTVAR = 0.75 × 25 + 0.25 × 20 = 23.75 ms; SRTT = 0.875 × 100 + 0.125 × 120 = 102.5 ms. RTO = 102.5 + 4 × 23.75 = 197.5 ms.
2. Second sample R = 80: |102.5 − 80| = 22.5; RTTVAR = 0.75 × 23.75 + 0.25 × 22.5 = 23.44 ms; SRTT = 0.875 × 102.5 + 0.125 × 80 = 99.69 ms. RTO = 99.69 + 4 × 23.44 = 193.4 ms.

[Result: RTO = 197.5 ms, then 193.4 ms. RTTVAR is updated first, using the old SRTT; real stacks then clamp the RTO to a minimum, 200 ms on Linux (RFC 6298 recommends 1 s).]{.result}
:::

Waiting for a timeout is slow, so TCP also uses *fast retransmit*: when three duplicate ACKs arrive, the sender retransmits the missing segment at once. The number three is a compromise. One or two duplicates can be produced by simple reordering in the network, which would cause needless retransmissions; waiting for more costs time on small windows. *Selective acknowledgements* (SACK) refine this: the receiver lists, in an option, the blocks of data it holds above the hole, so that the sender repairs several holes in one round trip and resends nothing that has arrived.
