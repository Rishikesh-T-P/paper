## [3.10]{.sec}The application layer: DNS, HTTP, TLS and QUIC [Should · ■■□]{.tag} {#s3-10}

The application layer is where users' programs meet the network. This section covers the four protocols that every web request touches: DNS to find the address, HTTP to ask for the page, TLS to protect it and QUIC to carry it faster. Google, Microsoft and Amazon treat it as a Must; for the other companies it is background for the capstone that follows.

::: bigidea
DNS turns names into addresses through a hierarchy of servers that cache their answers, and the HTTP, TLS and transport protocols beneath a web page have been reorganised, step by step, to need fewer round trips.
:::

### DNS

The *Domain Name System* is a distributed, hierarchical database that maps names to data, chiefly addresses. The hierarchy is read right to left: the *root* (written as a final dot) delegates to *top-level domains* such as `com.`, which delegate to organisations such as `google.com.`, whose own servers hold the records. Three roles take part. A *stub resolver*, inside every host, sends a single question to a configured resolver (the address is normally supplied by DHCP). A *recursive resolver*, run by the ISP, a company or a public service such as 8.8.8.8 or 1.1.1.1, does the work of finding the answer and caches it. An *authoritative server* holds the records of a zone and answers for it. The client's query is *recursive* ("find it for me"); the resolver's queries to the hierarchy are *iterative* ("tell me who to ask next"), because each server replies with an answer or a *referral*.

Every record has a type and a *time to live* (TTL), the number of seconds that a cache may keep it. The types to know are in the table. | Type | Holds | Note |

| NS | Names of a zone's authoritative servers | Used in referrals |
| MX | Mail servers with a priority | |
| PTR | Name for an address | Reverse lookup, under in-addr.arpa |

DNS uses UDP port 53 for ordinary queries, because a question and answer fit in one datagram each. It falls back to TCP port 53 when an answer is too large and the server sets the truncation flag, and always for zone transfers between servers. The extension mechanism EDNS0 allows UDP answers beyond the original 512 bytes. DNSSEC adds digital signatures to records so that a resolver can detect forgery; DNS over TLS (port 853) and DNS over HTTPS (port 443) encrypt the queries. A CNAME cannot be placed at a zone apex such as `example.com.`, since the apex must also hold SOA and NS records, and a CNAME may not share its name with other records. Hosting providers therefore offer a flattened alias (ALIAS or ANAME), which the authoritative server resolves itself and returns as ordinary A records.

::: example
**Follow `dig +trace www.google.com`, then watch the cache.**

1. The resolver starts with the root hints and asks a root server. The reply is a referral: the NS records of `com.`, with a TTL of 172800 s (two days), such as `a.gtld-servers.net`.
2. It asks a `com.` server, which refers it to the NS records of `google.com.` (`ns1.google.com` and others), again with a TTL of 172800 s.
3. It asks `ns1.google.com`, which is authoritative and returns the A record, with a short TTL such as 300 s, because Google may change it often.
4. Query `dig www.google.com @8.8.8.8` twice, ten seconds apart: the first answer shows TTL 300 or less, and the second shows about 10 less: the resolver is serving its cache and decrementing the TTL.

[Result: three iterative steps for a cold cache, none for a warm one. The answer is cached for 300 s; the NS records are cached for two days, so later lookups under `.com` skip the root and TLD steps.]{.result}
:::

### HTTP

The *Hypertext Transfer Protocol* is a request-response protocol over TCP (or QUIC). A request names a *method* (GET fetches, POST submits, PUT replaces, DELETE removes, HEAD fetches headers only), a path and headers; the response carries a *status code* and a body. The code classes are 1xx informational, 2xx success (200), 3xx redirection (301 permanent, 302 temporary, 304 not modified), 4xx client error (400, 401, 403, 404, 429 too many requests) and 5xx server error (500, 502 bad gateway, 503 unavailable). HTTP/1.0 opened a new TCP connection per request. HTTP/1.1 keeps the connection open (*persistent connections*), but answers requests in order, so browsers open six or so connections per site.

*HTTP/2* sends binary *frames* belonging to numbered *streams*, so that many requests share one TCP connection, interleaved, and compresses the headers (HPACK). It fixes the blocking at the HTTP level but not at the TCP level: a lost segment holds back every stream behind it. *HTTP/3* therefore runs over *QUIC*, a transport built on UDP (port 443) in which each stream is delivered independently, loss recovery and congestion control run in the application, TLS 1.3 is part of the handshake, and a *connection ID* lets a connection survive a change of IP address, as when a phone moves from Wi-Fi to cellular. A client that has talked to the server before may send data in the first flight (*0-RTT*), at the price of replay risk for that data.

### TLS, in one paragraph

*TLS* encrypts and authenticates the connection. The client sends its supported versions and ciphers, a key share and the *server name indication* (SNI), which names the site wanted so that one address can serve many; the server answers with its key share and a *certificate* signed by a certificate authority that the client trusts, proving that the key belongs to the name, and both sides derive the session keys from the key shares. TLS 1.3 completes this in one round trip, whereas TLS 1.2 needs two. The details, certificate chains and attacks are treated in Pillar 9, Section 9.4; here only the round-trip count matters, because it adds to the time to first byte, as Section 3.11 shows.

Other application protocols appear in questions about ports. They are collected below, and the ports are repeated in the Revision Spread.

| Protocol | Port | Purpose |
|---|---|---|
| SMTP; POP3; IMAP | 25 (587 submission); 110; 143 | Send mail; fetch and delete; synchronised mailbox |
| FTP | 21 control, 20 data (active) | Active: the server connects back to the client. Passive: the client opens the data connection, which works through NAT |
| SSH; Telnet | 22; 23 | Encrypted remote shell; the same in clear text |
| SNMP; NTP | 161/162; 123 (UDP) | Monitoring; time synchronisation |

## [3.11]{.sec}Capstone: what happens when you type google.com and press Enter [Must · ■■□]{.tag} {#s3-11}

This is the most commonly asked networking question in the book, because every concept in the pillar occurs in it. It is a poor question for a memorised monologue, since the interviewer will interrupt at the point where one is weakest. We therefore give a scaffold of eleven steps, then three versions of the answer at different depths, then the interruptions to expect.

::: bigidea
A strong answer is ordered, layered and quantified: it follows the packets in time, names the protocol and the address at each step, and says roughly how long each step takes.
:::

### The eleven steps

1. **Parse and local checks.** The browser splits the URL into scheme, host and path, consults its HSTS list (a site that demands HTTPS is upgraded before any request), and looks in its own DNS cache, the operating system's cache and the hosts file.
2. **DNS.** If the name is unknown, the stub resolver sends a UDP query to port 53 of the resolver learnt from DHCP. The resolver, if its cache is cold, resolves iteratively through root, `com.` and `google.com.` servers (Section 3.10) and returns the A and AAAA records.
3. **ARP (or NDP).** The destination is off-subnet, so the frame goes to the default gateway; if its MAC address is not cached the host broadcasts an ARP request first (Section 3.6).
4. **TCP.** A three-way handshake to port 443 (about one round trip); or, if the browser knows that the site speaks HTTP/3, a QUIC handshake over UDP 443.
5. **TLS 1.3.** ClientHello with SNI, ServerHello with key share, certificate validation against trusted authorities, Finished messages: one more round trip.
6. **HTTP.** The browser sends `GET / HTTP/2`. Google's address is *anycast*, so the packets reach the nearest front end, which may answer `301` or `200`.
7. **At every router:** the TTL is decremented and the checksum updated, a longest-prefix match chooses the next hop, and the Ethernet header is rewritten (Section 3.8). At the home router, PAT rewrites the source address and port (Section 3.6).
8. **Inside Google:** the front end terminates TLS and forwards to a load balancer and then to backend servers (Pillar 5).
9. **The response** returns by the reverse path, through the NAT table to the laptop; the sender's initial window of about ten segments determines how much arrives in the first round trip (Section 3.9).
10. **Rendering.** The browser parses the HTML and requests the subresources (images, scripts, styles), which reuse the open connection or open new streams.
11. **Reuse and teardown.** The connection stays open for later requests (keep-alive, HTTP/2 multiplexing) and is closed after an idle period with FIN or, for QUIC, with a close frame.

### Version 1: the 60-second answer

"The browser checks its caches and HSTS list, then DNS turns `www.google.com` into an IP address: my stub resolver asks the resolver given by DHCP, which asks root, `com.` and Google's servers if it has no cached answer. My host sees that the address is outside my subnet, so it ARPs for the default gateway and sends frames to its MAC address. A TCP handshake opens a connection to port 443, then a TLS handshake agrees keys and checks Google's certificate. The browser sends an HTTP GET; each router along the way decrements the TTL and forwards by longest-prefix match, rewriting the Ethernet header, and my home router translates my private address by PAT. Google's nearest front end answers, the reply comes back through the NAT table, and the browser renders the page, reusing the connection for the other files."

### Version 2: the 5-minute answer

Add the following to the scaffold, in this order. Say that DNS usually asks for both A and AAAA, and that a browser prefers IPv6 but races both ("happy eyeballs") so that a broken IPv6 path costs milliseconds, not seconds. At the link layer, name the frame fields: destination MAC is the gateway's, source MAC is the laptop's, and the IP header has TTL 64 and DF set. At TCP, give the sequence numbers' behaviour (random ISN, SYN consuming one number), the options in the SYN (MSS 1,460, window scale, SACK, timestamps) and the initial congestion window of 10 segments. At TLS, state that the client lists `h2` and `http/1.1` in ALPN, so the protocol is chosen inside the handshake, and that a 1.3 handshake costs one round trip. Finish with the numbers of the timeline: with a 15 ms round trip to the front end and 20 ms to a cold DNS resolver, DNS costs 20 ms, TCP 15 ms and TLS 15 ms, so the request leaves at about 50 ms and the first byte arrives at about 70 ms; QUIC saves one round trip by merging transport and TLS set-up, and a warm DNS cache saves nearly all of the first 20 ms.

### Version 3: the 15-minute answer, with interruptions

At this depth, the interviewer interrupts. The answers below are the expected ones; each points to its home section.

*"What if DNS is cached?"* The query never leaves the machine (browser or OS cache), or stops at the resolver (about 1 ms on a home network), and the 20 ms of the example disappears. The TTL decides how long this lasts (Section 3.10).

*"What if the gateway's MAC is unknown?"* The host holds the packet, broadcasts an ARP request on the LAN, and sends the frame when the reply arrives; this adds a fraction of a millisecond. If nobody replies, ARP fails and the connection attempt reports "host unreachable" after a few seconds (Section 3.6).

*"What if the certificate has expired, or names another host?"* The handshake completes at the TCP level but the client aborts at validation with a fatal alert and the browser shows a warning; no HTTP is sent. For a site with HSTS the user cannot click through (Pillar 9).

*"How does the reply find my laptop behind NAT?"* The reply is addressed to the router's public address and port; the router looks up the port in its translation table, rewrites the destination to the laptop's private address and port, and sends the frame to the laptop's MAC (Section 3.6).

*"What changes with HTTP/3?"* Steps 4 and 5 merge into one QUIC round trip over UDP 443; streams are independent; and the browser learned of HTTP/3 from an Alt-Svc header or an HTTPS DNS record (Section 3.10).

*"What if the first packet is bigger than the path MTU?"* The ClientHello is small, but a large response is not: TCP segments of at most the MSS avoid it, and a blocked ICMP 3/4 would cause the black hole of Section 3.5.

*"Why is the first page load slower than the second?"* The first load pays for DNS, TCP and TLS set-up and a small congestion window; the second reuses the connection, whose window has grown (Section 3.9).

*"Where does the load balancer sit?"* After TLS termination, at the front end; the choice of backend is made by a layer-7 or layer-4 balancer (Pillar 5).
