::: {.p4}

## [4.6]{.sec}EIGRP [Optional · ■■□]{.tag} {#s4-6}

::: bigidea
EIGRP is Cisco's advanced distance-vector protocol: it keeps a pre-verified loop-free backup path, the feasible successor, so that when the best path fails the router switches at once without asking its neighbours.
:::

EIGRP (IP protocol 88, multicast 224.0.0.10) forms neighbours when the autonomous-system number, the K values, the subnet and any authentication match. It sends Hello, Update, Query, Reply and ACK packets, using its own reliable transport. The *DUAL* algorithm works on these quantities for each destination: the *reported distance* (RD) is the neighbour's own metric to the destination; the *feasible distance* (FD) is our best total metric; the *successor* is the neighbour on the best path. A neighbour is a *feasible successor* if its RD is below our FD, which is the *feasibility condition*. This guarantees the neighbour's path does not pass through us, because a path through us would have an RD at least as large as our FD, and so it is loop-free by construction.

With the default K values (K1 = K3 = 1) the classic metric is 256 × (10^7 / lowest bandwidth in kb/s + sum of delays in tens of microseconds), each part as an integer. Wide metrics (64-bit) replace this on named-mode configurations so that 10 Gb/s and faster links remain distinguishable.

::: example
**An EIGRP metric and a feasibility test.**

1. *Metric.* A path crosses a T1 (1544 kb/s, delay 20,000 µs) and a Gigabit link (delay 10 µs). Bandwidth term: 10^7 / 1544 = 6476. Delay term: (20,000 + 10) / 10 = 2001. Metric = 256 × (6476 + 2001) = 2,170,112.
2. *Feasibility.* Paths to 10.9.9.0/24 are: via R2, FD 3000 (RD 1000), the successor; via R3, RD 2500; via R4, RD 3500. R3's RD 2500 is below 3000, so R3 is a feasible successor. R4's RD 3500 is not, so it is not feasible (it might loop).
3. *Variance.* With `variance 2` EIGRP may also use paths whose FD is below 2 × 3000 = 6000. R3 qualifies if its FD is below 6000. R4 is never used, because unequal-cost load balancing still requires feasibility.

[Result: 2,170,112; the feasible successor is R3; the used paths are R2 and R3.]{.result}
:::

If the successor fails and a feasible successor exists, it is promoted instantly and no packet is sent. If none exists, the router goes *active* for the route and sends *queries* to its neighbours, which may query theirs in turn. A route whose replies do not arrive in three minutes becomes *stuck in active* (SIA) and the neighbour is reset. Two defences limit this: *summarisation* (a query for a prefix covered by a summary is answered at once) and *EIGRP stub* routers, which are not asked at all.

If no feasible successor exists, the router does not simply fail over; it queries. The query spreads outwards until a router either has an answer or is a *stub*. Thus the size of the *query domain* determines how long convergence takes and how likely SIA is, which is why large EIGRP networks use summarisation at distribution layers and stubs at branches.

## [4.7]{.sec}BGP: the routing protocol of the Internet [Must · ■■■]{.tag} {#s4-7}

::: bigidea
BGP is a path-vector protocol between autonomous systems that carries policy attributes with each route, and the best route to each prefix is chosen by an ordered list of tie-breakers; it is thus the tool with which operators choose where traffic goes, rather than simply find the shortest path.
:::

An *autonomous system* (AS) is a set of networks under one administration with a single routing policy, identified by an AS number: 16-bit (1 to 65535, with 64512 to 65534 private) or 32-bit (private range 4,200,000,000 and above). BGP between routers of different ASes is *eBGP*; between routers of the same AS it is *iBGP*. BGP runs over TCP port 179, which provides reliable delivery and removes the need for BGP to retransmit. A route is advertised as *NLRI* (a prefix and length) together with *path attributes*, the most important of which, the AS_PATH, is the list of ASes the advertisement has crossed. A router rejects any route whose AS_PATH contains its own AS, which is the loop-prevention rule.

Messages: OPEN (version, AS number, hold time, BGP identifier, capabilities), UPDATE (withdrawn prefixes, path attributes, NLRI), KEEPALIVE, NOTIFICATION (an error; the session closes) and ROUTE-REFRESH. Cisco's default timers are keepalive 60 s and hold time 180 s, and the lower of the two peers' hold times is used.

Neighbours are configured explicitly (BGP does not discover them). An eBGP session between directly connected addresses needs only the address and the AS number. An iBGP session is best run between *loopbacks*, because a loopback stays up as long as any path exists, so `update-source Loopback0` tells BGP to originate the TCP session from that address. eBGP sessions between loopbacks (to use several parallel links) need `ebgp-multihop 2`, since the default TTL of 1 would expire at the first router.

BR1(config-router)# bgp router-id 10.255.0.1

BR1(config-router)# neighbor 10.255.0.2 remote-as 65000        ! iBGP, loopback
BR1(config-router)# neighbor 10.255.0.2 update-source Loopback0

The states are: *Idle* (no resources allocated; waiting for a start event, and a persistent Idle often means no route to the neighbour or a refused session); *Connect* (a TCP connection is being attempted); *Active* (the attempt failed and the router is retrying and listening: not a good state); *OpenSent* (OPEN sent, awaiting the peer's); *OpenConfirm* (OPEN accepted, awaiting a KEEPALIVE); *Established*. The last row explains the iBGP *full mesh*. Because a route learnt from one iBGP peer is not passed to another, every iBGP router must peer with every other, which needs n(n-1)/2 sessions: 45 for ten routers. Two remedies exist. A *route reflector* (RR) is allowed to break the rule: it reflects routes from *clients* to other clients and non-clients, and from non-clients to clients only, while a route learnt by eBGP goes to everyone. To avoid loops the RR tags a reflected route with an ORIGINATOR_ID (the first router's ID) and prepends its CLUSTER_ID to a CLUSTER_LIST; a router discards a route with its own ID, and an RR discards a route listing its own cluster. *Confederations* split the AS into sub-ASes that behave like eBGP among themselves.

Route reflection is configured on the reflector only; clients need no special configuration, and they cannot tell a reflector from a normal iBGP peer. The next hop is not changed by the RR, so an eBGP route reflected to a client still needs a reachable next hop.

::: example
**A reflector trace.** BR1 learns 203.0.113.0/24 from ISP-A and is a client of RR1 (router ID 10.255.0.100, cluster 10.255.0.100). RR1 also serves clients R3 and BR2.

1. BR1 sends the route to RR1 by iBGP with next hop BR1's loopback (`next-hop-self`).
2. RR1 reflects it to R3 and BR2, adding ORIGINATOR_ID = 10.255.0.1 and CLUSTER_LIST = {10.255.0.100}.
3. If a faulty configuration lets BR2 send the route back to RR1, RR1 sees its own cluster ID in the CLUSTER_LIST and discards it. If BR1 received its own route reflected back, it would see its own ORIGINATOR_ID and discard it.

A *confederation* is the other answer to the mesh. The AS is split into member sub-ASes (private numbers), full-meshed or reflected inside, with eBGP-like sessions between them that preserve LOCAL_PREF and next hop. The outside world sees only the confederation identifier. It is used rarely and mostly in legacy networks.

*Path attributes* come in four categories. *Well-known mandatory* attributes (ORIGIN, AS_PATH, NEXT_HOP) must be understood and sent with every route; *well-known discretionary* (LOCAL_PREF, ATOMIC_AGGREGATE) must be understood but need not be sent; *optional transitive* (COMMUNITY, AGGREGATOR) are passed on even if not understood; *optional non-transitive* (MED, ORIGINATOR_ID, CLUSTER_LIST) are dropped if not understood. **WEIGHT** is a Cisco-local value that is never sent to a peer.

| Attribute | Scope and use | Winner |
|---|---|---|
| WEIGHT | one router; Cisco only; default 0 (32768 for local routes) | highest |
| LOCAL_PREF | whole AS; sent only in iBGP; default 100; steers *outbound* traffic | highest |
| AS_PATH | list of ASes crossed; length is a distance proxy | shortest |
| ORIGIN | IGP (i) < EGP (e) < incomplete (?) | lowest |
| MED | sent to a neighbouring AS to suggest an entry point; steers *inbound* | lowest |
| COMMUNITY | a 32-bit tag that carries policy requests | n/a |

When a router holds several routes to a prefix, it selects *one* by this list; the first test that gives a unique winner stops the process. The Cisco order is shown. A short mnemonic is **"N WLLA OMNI"** for steps 0 to 8, then **"Old Routers Clear Neighbours"** for the final four.

| Step | Test | Rule |
|---|---|---|
| 0 | **N**ext hop reachable | unreachable routes are ignored |
| 1 | **W**eight | highest |
| 2 | **L**ocal preference | highest |
| 3 | **L**ocally originated | prefer own (network, aggregate, redistribute) |
| 4 | **A**S_PATH length | shortest |
| 5 | **O**rigin | lowest (IGP, then EGP, then incomplete) |
| 6 | **M**ED | lowest, compared only between routes from the *same neighbouring AS* |
| 7 | **N**eighbour type | eBGP over iBGP |
| 8 | **I**GP metric to next hop | lowest |
| 9 | multipath check | install several if `maximum-paths` allows |
| 10 | **O**ldest | the oldest eBGP route, for stability |
| 11 | **R**outer ID | lowest |
| 12 | **C**luster-list length | shortest |
| 13 | **N**eighbour address | lowest |

[**Other vendors** — FRR follows nearly the same list (weight, local preference, ...). Junos has no weight; it compares route preference, then LOCAL_PREF, then AS_PATH, and the order of the later steps differs, so consult the vendor documentation.]{.margin}

::: example
**A path-selection race.** BR1 (AS 65000) holds three paths to 203.0.113.0/24. (a) from ISP-A by eBGP: AS_PATH 100 300, LOCAL_PREF 100, MED 50. (b) from ISP-B by eBGP: AS_PATH 200 300, LOCAL_PREF 100, MED 10. (c) from the iBGP peer BR2: AS_PATH 100 300, LOCAL_PREF 150.

1. Weight is unset on all three, so no decision at step 1.
2. Step 2: local preference 150 beats 100. **(c) wins** and the process stops.

Now remove the local-preference setting on (c), so all are 100.

3. Steps 3 to 5 tie: no path is local, all three have AS_PATH length 2 and the same origin.
4. Step 6, MED. MED is compared only between routes from the same neighbouring AS. (a) and (c) both come from AS 100, but (b) comes from AS 200, so (b)'s lower MED is *not* compared against (a).
5. Step 7: eBGP is preferred to iBGP, so (c) is eliminated. (a) and (b) tie through step 8 (equal IGP cost to directly connected peers).
6. Step 10: the oldest eBGP path wins, so whichever was learnt first stays, which is unpredictable by design.

[Result: (c) on LOCAL_PREF; without it, (a) or (b) by age. With `bgp always-compare-med`, step 6 would compare (a) and (b) too, and (b) would win with MED 10.]{.result}
:::

::: example
**Dual-homing Campus Net.** BR1 connects to ISP-A (AS 100) and BR2 to ISP-B (AS 200); Campus Net (AS 65000 in this teaching topology) owns 198.51.100.0/24. The goal is for ISP-A to be primary in both directions.

1. *Outbound*: local preference is the tool, since it is shared across the AS by iBGP. Set 200 on routes learnt from ISP-A.
2. *Inbound*: remote ASes decide, so we make the ISP-B path look longer by prepending our AS twice when advertising to ISP-B.

```
! BR1
ip route 198.51.100.0 255.255.255.0 Null0
ip prefix-list OUT seq 5 permit 198.51.100.0/24
route-map FROM-A permit 10
 set local-preference 200
router bgp 65000
 neighbor 192.0.2.1 remote-as 100
 neighbor 192.0.2.1 route-map FROM-A in
 neighbor 192.0.2.1 prefix-list OUT out
 neighbor 192.0.2.1 maximum-prefix 1000 80
 neighbor 10.255.0.2 remote-as 65000
 neighbor 10.255.0.2 update-source Loopback0
 neighbor 10.255.0.2 next-hop-self
 network 198.51.100.0 mask 255.255.255.0
! BR2
route-map TO-B permit 10
 set as-path prepend 65000 65000
router bgp 65000
 neighbor 192.0.2.5 remote-as 200
 neighbor 192.0.2.5 route-map TO-B out
```

```
BR1# show ip bgp 203.0.113.0/24
   Network          Next Hop     Metric LocPrf Weight Path
*> 203.0.113.0/24   192.0.2.1         0    200      0 100 300 i    <-- best (>), via ISP-A
* i                 10.255.0.2        0    100      0 200 300 i
```

[Result: Campus Net sends via ISP-A (LOCAL_PREF 200). Remote networks see paths "100 65000" and "200 65000 65000 65000" and prefer the shorter one via ISP-A.]{.result}
:::

::: example
**The iBGP next-hop problem.** R3, an internal Campus Net router, is an iBGP client of BR1 and has no eBGP session. BR1 learns 203.0.113.0/24 with next hop 192.0.2.1 and passes it to R3 *unchanged*. R3's IGP has no route to 192.0.2.1, so the next hop is unreachable.

```
R3# show ip bgp
   Network          Next Hop     Metric LocPrf Weight Path
 * i203.0.113.0/24  192.0.2.1          0    100      0 100 300 i   <-- no ">": not best, not in RIB
```

[Result: add `neighbor 10.255.0.3 next-hop-self` on BR1, so the next hop becomes BR1's loopback, which the IGP knows. Alternatively advertise the ISP link into the IGP as a passive interface.]{.result}

::: example
**A five-path race.** BR1 has five candidates for 203.0.113.0/24. None of them has a weight set. Step through the list.

| Path | LOCAL_PREF | Local | AS_PATH | Origin | MED | Type | IGP metric to NH | Router ID |
|---|---|---|---|---|---|---|---|---|
| P1 | 100 | no | 100 300 | i | 20 | eBGP | 0 | 10.0.0.9 |
| P2 | 100 | no | 100 300 | i | 5 | eBGP | 0 | 10.0.0.7 |
| P3 | 100 | no | 200 400 500 | i | 0 | eBGP | 0 | 10.0.0.5 |
| P4 | 100 | no | 100 300 | i | 5 | iBGP | 10 | 10.255.0.2 |
| P5 | 90 | no | 100 | e | 0 | eBGP | 0 | 10.0.0.3 |

1. Step 0 and 1: all next hops reachable; weights tie.
2. Step 2: LOCAL_PREF 100 beats 90. **P5 is eliminated**, though it has the shortest AS_PATH: policy comes before distance.
3. Step 3: no local routes. Step 4: AS_PATH length: P1, P2 and P4 have 2, P3 has 3. **P3 is eliminated.**
4. Step 5: origin ties (all IGP). Step 6: MED, compared among paths from the same neighbouring AS (all three remaining come from AS 100): P2 and P4 have 5, P1 has 20. **P1 is eliminated.**
5. Step 7: eBGP over iBGP: **P4 is eliminated**; P2 remains.

[Result: P2 wins at step 7. Had P2 and P4 both been eBGP, step 8 (IGP metric), then step 10 (age) and step 11 (router ID 10.0.0.7 against another) would have decided.]{.result}
:::

*Communities* and *aggregation* complete everyday practice. A community is set with a route map (`set community 65000:100 additive`) and sent to the neighbour only if `neighbor X send-community` is configured; the receiving AS then acts on it, for example by assigning local preference 80 to routes tagged 65000:80 (a *backup* community) or by blackholing a destination. `aggregate-address 198.51.100.0 255.255.255.0 summary-only` creates a summary (and suppresses the more-specific components); an aggregate that loses detail sets ATOMIC_AGGREGATE and may carry an AGGREGATOR attribute (and an AS_SET).

```
ip as-path access-list 10 permit ^100_            ! learnt from AS 100
ip as-path access-list 20 permit ^$               ! originated locally
ip community-list standard BACKUP permit 65000:80
route-map FROM-ISP permit 10
 match community BACKUP
 set local-preference 80
route-map FROM-ISP permit 20
router bgp 65000
 neighbor 192.0.2.5 route-map FROM-ISP in
 neighbor 192.0.2.5 send-community
```

Convergence is mostly a timer problem. With default timers a silent failure is noticed only after the hold time (180 s). `fast-external-fallover` (on by default) resets an eBGP session the moment its directly connected interface goes down, and *BFD* (`neighbor X fall-over bfd`) detects loss in a fraction of a second. After a policy change `clear ip bgp X soft in` applies the new inbound policy using a stored copy or a ROUTE-REFRESH, without resetting the session. Two further knobs are the advertisement interval (30 s for eBGP by default) and graceful restart.

Policy tools complete the picture. *Outbound* traffic is influenced by weight (one router) and local preference (the whole AS). *Inbound* traffic can only be influenced indirectly: AS-path prepending, MED (honoured only by the neighbouring AS), advertising more-specific prefixes (most of the Internet filters beyond /24), and communities that ask the provider to act. The well-known communities are `no-export` (do not advertise outside this AS) and `no-advertise` (do not advertise to any peer). Filtering uses prefix lists ([§4.9](#s4-9){.ref}), AS-path access lists with regular expressions (`^$` means locally originated, `_65001_` any path through AS 65001) and route maps, with `maximum-prefix` as a safety valve, and `soft-reconfiguration inbound` or route refresh to re-apply a policy without resetting the session.

The `network` command in BGP advertises a prefix only if an *exact* match is present in the RIB (which is why the Null0 route above is configured), unlike the `network` command of OSPF, which selects interfaces. `maximum-paths 4` installs several equal paths, provided the weight, local preference, AS_PATH length, origin, MED, neighbouring AS and IGP cost all match; `bgp bestpath as-path multipath-relax` relaxes the requirement that the AS numbers be identical, which suits spine-leaf fabrics where each leaf has its own AS. Those designs (RFC 7938) use eBGP alone because of its policy control and its simple failure behaviour; see [§5.4](#s5-4){.ref}.

BGP is trusted by configuration, not by proof. In 2008 a Pakistani ISP's attempt to block YouTube leaked a more-specific prefix to the world, and most of the Internet followed the longer prefix; in 2021 a configuration change withdrew a large content provider's prefixes and took its DNS servers off the Internet with them. The defences are origin validation with RPKI (route origin authorisations decide whether a route is *valid*, *invalid* or *not found*), prefix and `maximum-prefix` limits, MD5 or TCP-AO session authentication, and the generalised TTL security mechanism (`ttl-security hops 1`).

A note on AS numbers: Campus Net uses the private AS 65000 in this book's examples. A private AS cannot be used on the Internet's global table, so a provider strips it (`neighbor X remove-private-as`) before advertising the customer's prefix. That suits a customer attached to one provider; a customer that is dual-homed, as in Figure 4.13, needs a public AS number, since otherwise the prefix would appear to originate from two different ASes and origin validation could not be applied.


::: trap
*Claim:* a lower MED always wins, so (b) with MED 10 beats (a) with MED 50. *Why it is wrong:* by default MED is compared only between routes from the same neighbouring AS, and these come from AS 200 and AS 100. *Correct statement:* the comparison is skipped unless `bgp always-compare-med` is configured. Note also that MED is lower-wins, whereas weight and local preference are higher-wins.
:::

::: trap
*Claim:* "BGP neighbour Active" means the session is working. *Why it is wrong:* Active means the router is *trying* to open the TCP connection and has failed. *Correct statement:* a healthy session is Established; Active or Idle is a fault, usually reachability, ACL, a wrong AS number or a missing `update-source`.
:::
