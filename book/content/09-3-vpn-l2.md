## [9.7]{.sec}IPsec and IKE [Must · ■■■]{.tag} {#s9-7}

::: bigidea
IPsec protects traffic at the IP layer for every application at once, and it separates the work into a slow, rare negotiation (IKE) and a fast, per-packet protection (ESP), because the keys must be agreed before any packet can be encrypted.
:::

*IPsec* is a suite of protocols that authenticates and encrypts IP packets. It has two data-plane protocols and one control protocol. *ESP* (Encapsulating Security Payload, IP protocol 50) gives confidentiality, integrity and replay protection. *AH* (Authentication Header, protocol 51) gives integrity and replay protection only, and it authenticates parts of the outer IP header, so any NAT that rewrites an address breaks it; hence ESP with integrity is the norm and AH is rarely seen. *IKE* (Internet Key Exchange, UDP 500) authenticates the peers and creates the keys.

Each protected direction of traffic is described by a *Security Association* (SA): the algorithms, the keys, the lifetime and a 32-bit *Security Parameter Index* (SPI) that the receiver uses to look up the SA in its database. SAs are one-way, so a tunnel needs a pair. The *Security Policy Database* (SPD) says which traffic is to be protected, bypassed or dropped; the *Security Association Database* (SAD) holds the live SAs.

IPsec works in two modes (Figure 9.10). In *transport mode* the original IP header is kept and ESP is inserted between it and the transport header; this protects host-to-host traffic. In *tunnel mode* the whole original packet is encrypted and a new outer IP header added; this is used between gateways, and it hides the inner addresses. When a NAT device lies on the path, ESP has no ports for the NAT to translate. *NAT traversal* (NAT-T) solves this by wrapping ESP in a UDP header, port 4500, after IKE detects the translation from hashes of the addresses it sends.

IKE negotiates in two stages. In *IKEv1*, Phase 1 builds a protected IKE channel, in six messages in *main mode*, or three in *aggressive mode*, which is faster but exposes the peer identities and a hash that allows offline guessing of a pre-shared key; Phase 2, *quick mode*, uses that channel to build the IPsec SAs in three messages. The embassy analogy fits: Phase 1 is two embassies agreeing on a secure diplomatic pouch, and Phase 2 is the individual sealed letters sent in it. *IKEv2* (RFC 7296) simplifies this (Figure 9.11). `IKE_SA_INIT` (two messages) agrees on the algorithms, exchanges DH values and nonces and creates the IKE SA. `IKE_AUTH` (two messages), encrypted, exchanges identities, proves them by pre-shared key, certificate or EAP, and negotiates the first *Child SA* (the ESP tunnel) with the *traffic selectors*. Four messages thus replace six or nine. `CREATE_CHILD_SA` later adds a Child SA or rekeys either SA, and liveness checks and EAP support are built in.

For two peers to bring a tunnel up, the following must match: the encryption and integrity algorithms (or the AEAD), the pseudo-random function, the DH group, the authentication method and key, and the lifetimes; if *perfect forward secrecy* (PFS) is configured, a new DH exchange is performed for each Child SA, so that compromise of the IKE keys does not expose later Child SAs. The traffic selectors (the *proxy-IDs* or crypto ACL of policy-based VPNs) must mirror each other. A *policy-based* VPN protects the traffic that matches an ACL; a *route-based* VPN creates a virtual tunnel interface (VTI), and whatever the routing table sends into it is protected, which is simpler and supports routing protocols over the tunnel.

::: example
**A site-to-site tunnel from Campus Net to its hostel annex.** BR1 (203.0.113.2) protects traffic between ENG, 192.168.20.0/24, and the annex, 172.16.50.0/24, whose router has public address 198.51.100.20. Route-based IKEv2 on IOS XE:

```
crypto ikev2 proposal P1
 encryption aes-gcm-256
 prf sha256
 group 19
crypto ikev2 policy POL1
 proposal P1
crypto ikev2 keyring KR1
 peer ANNEX
  address 198.51.100.20
  pre-shared-key <secret>
crypto ikev2 profile PROF1
 match identity remote address 198.51.100.20 255.255.255.255
 authentication local pre-share
 authentication remote pre-share
 keyring local KR1
crypto ipsec transform-set TS1 esp-gcm 256
 mode tunnel
crypto ipsec profile IPSEC1
 set transform-set TS1
 set ikev2-profile PROF1
interface Tunnel0
 ip address 10.255.0.1 255.255.255.252
 tunnel source GigabitEthernet0/0
 tunnel destination 198.51.100.20
 tunnel mode ipsec ipv4
 tunnel protection ipsec profile IPSEC1
ip route 172.16.50.0 255.255.255.0 Tunnel0
```

1. The proposal fixes the algorithms: AES-256 in GCM mode (so no separate integrity algorithm), SHA-256 as the PRF and DH group 19 (the 256-bit NIST curve).
2. The profile names the peer and the authentication; the IPsec profile binds the transform set to it; `tunnel protection` attaches both to the interface.
3. The static route sends annex traffic into the tunnel, and the router encrypts it after the routing decision.
4. Verify in two places, since the IKE SA and the Child SA are separate:

```
BR1# show crypto ikev2 sa
 Tunnel-id  Local            Remote            Status
 1          203.0.113.2/500  198.51.100.20/500 READY
BR1# show crypto ipsec sa | include encaps|decaps
  #pkts encaps: 124, #pkts encrypt: 124
  #pkts decaps: 122, #pkts decrypt: 122
```

[Result: status READY and both counters rising mean the tunnel carries traffic in both directions; READY with counters at zero, or only one rising, points to routing or a Child SA problem.]{.result}
:::

*A planted fault.* Suppose the annex router is configured with a policy-based selector 172.16.50.0/25 while BR1 proposes 172.16.50.0/24. Phase 1 completes, `show crypto ikev2 sa` says READY, yet no traffic passes; the debug shows the responder answering the Child SA with the notification `TS_UNACCEPTABLE`. The cause is that the selectors do not mirror each other. This is why "phase 1 up" never means "the VPN works". The check order is then: the IKE SA state, the Child SA and its selectors, the transform set and PFS group, the routing into the tunnel, and finally NAT exemption (traffic to the annex must not be translated before it is encrypted). The full troubleshooting case is in [Pillar 11](#ch11){.ref}.

::: trap
*Claim:* AH is more secure than ESP because it authenticates the whole packet. *Why it is wrong:* AH gives no confidentiality, and because it covers the outer header it fails when NAT changes an address. *Correct statement:* ESP with an authenticated mode such as AES-GCM is the standard; AH is retained for completeness.
:::

## [9.8]{.sec}VPN families and remote access [Should · ■■□]{.tag} {#s9-8}

::: bigidea
A VPN builds a private path over a public network with encryption as the tunnel wall, and each family differs in the layer at which it works, the client it needs and how it survives NAT.
:::

A *site-to-site* VPN joins two networks and is invisible to users; IPsec is the classical choice. *Remote-access* VPNs connect one user device to the enterprise: either IPsec with IKEv2 and EAP, or an *SSL/TLS VPN* (such as Cisco Secure Client) that runs over TCP 443 and uses DTLS over UDP for speed. The TLS form passes almost every firewall because it looks like HTTPS, and some products offer a clientless portal. *WireGuard* is a newer design: peers are identified by public keys, handshake uses the Noise protocol with Curve25519, data uses ChaCha20-Poly1305 over UDP, and there is no negotiation of algorithms at all, which keeps the code small enough to audit. Cisco DMVPN and GETVPN are Cisco-specific ways of scaling IPsec to many sites; we mention the names only.

| | IPsec site-to-site | IPsec remote access | SSL/TLS VPN | WireGuard |
|---|---|---|---|---|
| Layer | 3 | 3 | 4 to 7 | 3 |
| Transport | ESP or UDP 4500 | ESP or UDP 4500 | TCP or UDP 443 | UDP (any port) |
| NAT traversal | NAT-T | NAT-T | native | native (UDP, keepalive) |
| Client | none (gateways) | native or vendor | vendor client or browser | small client, one key per peer |
| Authentication | PSK, certificate | certificate, EAP | certificate, SAML, MFA | public keys only |
| Typical use | branch to HQ | managed laptops | contractors, restrictive networks | site links, servers, personal VPN |

*Split tunnelling* sends only enterprise prefixes through the VPN and everything else directly to the Internet. It saves bandwidth, but the device is then on two networks at once and the enterprise cannot inspect its Internet traffic; full tunnelling reverses both properties.

Every encapsulation consumes bytes of the packet, so the inner MTU must shrink. For ESP in tunnel mode with AES-GCM over IPv4, the extra bytes are:

| Item | Bytes |
|---|---|
| New outer IP header | 20 |
| ESP header (SPI + sequence number) | 8 |
| GCM initialisation vector | 8 |
| Padding (0 to 3) + pad length + next header | 2 to 5 |
| Integrity check value (ICV) | 16 |
| **Total** | **54 to 57** |
| NAT-T UDP header | + 8 |

::: example
**Why `ip tcp adjust-mss 1360`.** On a 1500-byte path the worst case with NAT-T is 57 + 8 = 65 bytes, so the largest inner packet is 1500 − 65 = 1435 bytes. A TCP segment carries 40 bytes of IP and TCP headers, so the largest segment payload (MSS) is 1435 − 40 = 1395 bytes. Without a correction, hosts negotiate an MSS of 1460, their packets exceed the tunnel and either fragment or vanish (when DF is set and ICMP is filtered). The router therefore rewrites the MSS in SYNs that cross the tunnel. The common value of 1360 is conservative: it leaves 35 bytes of margin for GRE (24 bytes), PPPoE (8 bytes) or IPv6 on the path.
:::

WireGuard adds 60 bytes over IPv4 (20 IP, 8 UDP, 16 for its header and 16 for the authentication tag, plus padding of the inner packet to a multiple of 16), so its default tunnel MTU is 1420, which also suits IPv6 paths (80 bytes). The comparison for large deployments is made in Q9.32.

::: lab

## [9.9]{.sec}Layer-2 attacks and switch hardening [Must · ■■□]{.tag} {#s9-9}

::: bigidea
Layer-2 protocols trust every host on the segment, because ARP, DHCP, DTP and STP were designed for friendly networks; hardening replaces that trust with state kept by the switch.
:::

An attacker inside the building needs no firewall bypass: a laptop on a wall socket already shares a broadcast domain with its victims. The switch features of this section are cheap, run in hardware and are expected knowledge for any Cisco, Juniper or Nokia interview. The attacks and defences are collected in one table in the Revision Spread; here we explain how each works.

**ARP spoofing.** ARP ([Section 3.6](#s3-6){.ref}) has no authentication: any host may announce that an IP address is at its MAC address, and neighbours accept the latest claim. ARP spoofing exploits this. The attacker sends gratuitous ARP replies claiming that the gateway's address is at the attacker's MAC and that the victim's address is also at the attacker's MAC (Figure 9.12), so both ends send their frames to the attacker, who relays them: a *man-in-the-middle*. As a wedding guest shouting "I am the caterer!" collects all the dishes, the attacker collects the traffic.

**DHCP attacks.** In *DHCP starvation* the attacker requests addresses with forged MAC addresses until the pool is empty; then a *rogue DHCP server* answers new clients with the attacker as gateway and DNS server, which is another man-in-the-middle. **MAC flooding** floods the switch with frames from random source MACs until the table is full; the switch then floods unknown unicast frames out of every port in the VLAN, like a hub, and the attacker captures them ([Section 3.2](#s3-2){.ref}).

The defences work together.

- *Port security* limits the MAC addresses per access port (`maximum`), can learn them as `sticky` and reacts to a violation by `protect` (drop silently), `restrict` (drop and log) or `shutdown` (the default; the port is err-disabled until reset or recovered). It stops MAC flooding and starvation by forged MACs.
- *DHCP snooping* classifies ports as *trusted* (uplinks, the DHCP server) or *untrusted* (access). On untrusted ports it drops DHCP server messages (OFFER, ACK), so a rogue server is silent, and it can rate-limit DHCP requests, which blunts starvation. It also builds the *binding table*: MAC, IP address, VLAN, port and lease for every address handed out.
- *Dynamic ARP Inspection* (DAI) checks each ARP packet on an untrusted port against the binding table and drops those whose sender IP and MAC do not match a binding. It therefore *depends on DHCP snooping* (or on static ARP ACLs for hosts with fixed addresses). Uplinks are marked trusted.
- *IP Source Guard* uses the same table to drop packets whose source IP is not bound to the port, which limits spoofing from the inside.

::: example
**Hardening a Campus Net access switch.** SW1 serves SALES (VLAN 10) and ENG (VLAN 20) on Gi1/0/2 to Gi1/0/24, with the uplink to R1 on Gi1/0/1.

```
ip dhcp snooping
ip dhcp snooping vlan 10,20
ip arp inspection vlan 10,20
interface GigabitEthernet1/0/1
 description uplink to R1
 ip dhcp snooping trust
 ip arp inspection trust
interface range GigabitEthernet1/0/2 - 24
 switchport mode access
 switchport nonegotiate
 switchport port-security
 switchport port-security maximum 2
 switchport port-security violation restrict
 switchport port-security mac-address sticky
 ip dhcp snooping limit rate 15
 spanning-tree portfast
 spanning-tree bpduguard enable
```

```
%SW_DAI-4-DHCP_SNOOPING_DENY: 1 Invalid ARPs (Reply) on Gi1/0/5, vlan 10.
```

[Result: the victim's ARP table keeps the real gateway MAC, and the log names the port to investigate.]{.result}
:::

**VLAN hopping** lets an attacker reach a VLAN to which the port does not belong, in two ways. In *switch spoofing* the attacker's host speaks DTP (the dynamic trunking protocol) and negotiates a trunk with the switch if the port is `dynamic auto` or `desirable`, after which it receives the traffic of all VLANs. The cure is to set access ports to `switchport mode access` and `switchport nonegotiate`. In *double tagging* the attacker sits in the trunk's native VLAN (VLAN 1 by default) and sends a frame with two 802.1Q tags: the outer carries the native VLAN, the inner the target VLAN (Figure 9.13). The first switch removes the outer tag, since native-VLAN frames cross the trunk untagged, and forwards the frame still carrying the inner tag; the second switch reads it and delivers the frame into the victim VLAN. The attack is one-way (no reply can return the same way) and works only if the native VLAN matches an access VLAN in use. Hence the native VLAN of every trunk is set to an unused VLAN (for example VLAN 999), unused ports are shut down, and tagging of the native VLAN may be enforced.

::: trap
*Claim:* VLANs are a security boundary on their own. *Why it is wrong:* a misconfigured trunk, DTP, a shared native VLAN or an unfiltered router lets traffic cross, and traffic between VLANs passes the router, which has no filter unless an ACL is applied. *Correct statement:* VLANs separate broadcast domains; security needs hardened trunks, native-VLAN hygiene and filtering at Layer 3 (Section 9.5).
:::

**STP manipulation.** An attacker who sends BPDUs with a low bridge priority can become the root bridge and steer the whole network's traffic through his port. *BPDU Guard* on PortFast edge ports puts the port in err-disabled state on receiving any BPDU; *Root Guard* on distribution-facing ports refuses a superior BPDU and puts the port in a root-inconsistent state until it stops. Storm control additionally caps broadcast, multicast and unknown-unicast rates per port. STP itself is taught in [Section 4.3](#s4-3){.ref}.
