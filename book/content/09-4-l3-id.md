## [9.10]{.sec}Layer-3 and Layer-4 attacks, and DDoS [Must · ■■□]{.tag} {#s9-10}

::: bigidea
Most network floods succeed because a packet's source address is never checked and because the server commits memory before the client proves it exists; the cures are to verify the source and to postpone the commitment.
:::

**IP spoofing.** The IP header carries whatever source address the sender writes, and a router forwards on the destination only. Spoofing hides the attacker, and it is the basis of reflection attacks. The cure is *ingress filtering* (BCP 38, RFC 2827): the provider drops packets arriving from a customer whose source address is not in the customer's allocation. Inside a network, *unicast reverse path forwarding* (uRPF) does it automatically by asking, for each packet, whether the routing table would send traffic to the source address out of the arrival interface. In *strict* mode the best route must use that very interface, which suits single-homed edges. In *loose* mode any route to the source suffices, which is required where routing is asymmetric, as on a multihomed border such as BR1 and BR2, where a strict check would drop valid traffic. On IOS the commands are `ip verify unicast source reachable-via rx` (strict) and `reachable-via any` (loose).

**SYN flood.** The TCP handshake ([Pillar 3](#ch3){.ref}) makes a server allocate a half-open entry when a SYN arrives, and hold it for tens of seconds while waiting for the ACK. An attacker sends SYNs from random spoofed sources at a high rate. The entries fill the SYN queue (Figure 9.14, and Figure 7.17 for the queues of [Section 7.10](#s7-10){.ref}), the SYN-ACKs go to hosts that never asked, and genuine clients are refused. As a prankster who books every table at a restaurant and never arrives, the attacker uses very little of his own resources.

Defences: enlarge the backlog and shorten the SYN-ACK retry count (they only delay exhaustion); filter at the edge; place a *SYN proxy* in a firewall, which completes the handshake itself and passes the connection on only when the client answers; or use **SYN cookies**. With cookies the server, when its queue is full, stores nothing. It encodes the state in the initial sequence number of its SYN-ACK. In the original design the 32 bits hold 5 bits of a minute counter, 3 bits that index a small table of MSS values, and 24 bits of a keyed hash of the addresses, ports and counter; Linux uses a close variant that adds the counter and mixes the MSS index into a second hash. A genuine client returns acknowledgement number = ISN + 1, from which the server recomputes the hash, validates it and rebuilds the connection. A spoofed source never returns, so the attacker consumes no memory. The price is that options such as window scaling must be carried in other ways, so cookies are used only under load.

::: deep
**A cookie with numbers (illustrative layout).** Let the MSS table be {536, 1300, 1440, 1460}, the minute counter 17, and let the keyed hash of the two addresses, the two ports and the counter be 0x2A91F3.

1. Cookie = 17 × 2²⁷ + 3 × 2²⁴ + 0x2A91F3 = 2,281,701,376 + 50,331,648 + 2,789,875 = 2,334,822,899. This is the sequence number of the SYN-ACK; the acknowledgement number is the client's ISN plus 1.
2. The honest client replies with acknowledgement number 2,334,822,900.
3. The server subtracts 1, reads the counter (17, accepted if it is within the last two or so minutes) and the MSS index (3, so 1460), recomputes the hash and compares it with the low 24 bits.

[Result: a valid ACK recreates the connection with the right MSS, and nothing was stored in between.]{.result}
:::

**Other floods.** UDP and ICMP floods need no handshake and simply saturate a link or a CPU. *Smurf* attacks (an ICMP echo to a broadcast address with the victim's spoofed source) are historic because routers no longer forward directed broadcasts. *Application-layer* attacks send valid but expensive requests: an HTTP flood requests heavy pages, and *Slowloris* holds many connections open with partial requests until the server's connection table is full.

**Reflection and amplification.** The attacker sends a small query with the *victim's* address as source to many public servers, which answer the victim with a much larger reply (Figure 9.15). Protocols that use UDP and return more than they receive are used: DNS (reported factors of tens), NTP's old `monlist` command (hundreds), and memcached (up to tens of thousands). The attacker's own bandwidth is multiplied and the packets arrive from legitimate servers. The defences are in three places: BCP 38 stops the spoofing at the source network; server operators close open resolvers and disable `monlist` and UDP memcached; the victim needs capacity upstream.

**BGP hijacking.** An AS can announce a prefix it does not own, or a more specific one, and neighbours who do not check will route traffic to it ([Section 4.7](#s4-7){.ref}). The defence is *RPKI route origin validation* (ROV). The holder of a prefix signs a *ROA* (route origin authorisation) naming the prefix, its maximum length and the AS allowed to originate it. A router that validates classifies each route as *valid* (matches a ROA), *invalid* (covered by a ROA but with the wrong origin or too long) or *not found*, and drops the invalid ones. Limits: ROV checks only the origin, not the path, so an attacker who forges the legitimate origin at the end of the path is not caught (path validation by ASPA or BGPsec is still in development); and coverage is incomplete, since unsigned prefixes are "not found". Prefix filters, max-prefix limits and IRR-based filters supplement it.

DDoS attacks fall into three classes, which need different defences.

| Class | Example | Target | Main defence |
|---|---|---|---|
| Volumetric | UDP flood, amplification | bandwidth | upstream scrubbing, anycast, RTBH |
| Protocol | SYN flood, fragment flood | state tables, CPU | SYN cookies, SYN proxy, rate limits |
| Application | HTTP flood, Slowloris | the application | CDN and WAF, rate limiting per client, autoscaling |

A *DDoS defence stack* is layered, since no single device is large enough. At the edge, ACLs, uRPF and rate limits remove obvious junk. At the provider, *remotely triggered black hole* (RTBH) routing advertises the victim's address with a community that makes upstream routers discard its traffic, at the cost of giving the attacker the outage; *BGP Flowspec* distributes finer filters (by port or packet size). A *scrubbing centre* receives the victim's traffic through a BGP diversion or an anycast address, removes the attack and returns the clean traffic by a tunnel. A CDN and WAF absorb application floods, and at the origin cookies and autoscaling provide the last margin. Note that a stateful firewall is not on this list: its session table is itself a target, and a volumetric flood saturates the link before the firewall sees it.

## [9.11]{.sec}DNS security [Should · ■■□]{.tag} {#s9-11}

::: bigidea
Classical DNS answers are accepted on the strength of a 16-bit transaction ID and a UDP port, so security has to come either from making these unguessable or from signing the data.
:::

DNS ([Pillar 3](#ch3){.ref}) runs over unauthenticated UDP. In *cache poisoning* the attacker makes a recursive resolver ask for a name and then floods it with forged answers; the first answer that matches the query's name, transaction ID and source port is cached, and every client of the resolver is then sent to the attacker's address (Figure 9.16). It is like slipping a fake entry into the society telephone directory before the real one arrives.

The *Kaminsky attack* (2008) made this practical. A normal attacker has one chance per record, then must wait until the cached answer expires. Kaminsky queried *random* names under the target domain (aaaa1.example.com, aaaa2.example.com), which can never be cached, so each query started a fresh race; the forged answer carried an extra "authority" record that rewrote the name servers of the whole domain.

::: example
**Why source-port randomisation mattered.** Suppose the attacker sends 1,000 forged answers inside each race.

1. With a fixed port, only the 16-bit ID must be guessed: 1,000 / 65,536 ≈ 1.5 % per race. The chance of at least one win reaches 50 % after about 0.69 / 0.0153 ≈ 45 races, which takes seconds.
2. With a random port among about 64,000, the guess space is 65,536 × 64,000 ≈ 4.2 × 10⁹, so the chance per race is 1,000 / 4.2 × 10⁹ ≈ 2.4 × 10⁻⁷. Reaching 50 % takes about three million races, which is hours or days of sustained traffic and easy to notice.

[Result: 16 more random bits raise the attacker's work by about 65,000 times. Case randomisation of the query name (0x20) adds a few more bits.]{.result}
:::

Randomisation only raises the cost; *DNSSEC* removes the problem by signing the data (RFC 4033). Each zone has a key pair: the *DNSKEY* records publish the public keys, and an *RRSIG* record signs every record set. The parent zone vouches for the child's key with a *DS* record, which is a hash of the child's key-signing key, so the chain runs from the root (the resolver's *trust anchor*) through `com` to `example.com` (Figure 9.17). A validating resolver checks the chain and sets the AD (authenticated data) flag; if it fails, the client receives SERVFAIL. Denial of existence is signed too (NSEC and NSEC3 records). DNSSEC authenticates the origin of the data but encrypts nothing, and it does not protect the last hop between the client and its resolver unless that resolver is validating and trusted.

*DNS over TLS* (DoT, TCP 853) and *DNS over HTTPS* (DoH, TCP 443) encrypt the hop between client and resolver, which hides the queries from the local network and prevents tampering on that path. They do not prove that the answer is true, which is the job of DNSSEC. Because DoH looks like HTTPS, it also bypasses DNS-based filters, which is a concern for enterprise policy. Other threats: *DNS tunnelling* hides data in long, random-looking query names to an attacker's domain, detected by query length and volume; *open resolvers* are used as amplifiers and should answer only their own clients.

The two are complementary.

## [9.12]{.sec}AAA, RADIUS, TACACS+ and 802.1X [Should · ■■□]{.tag} {#s9-12}

::: bigidea
Network devices should not decide who may log in or connect; a central server does, so that identities, permissions and records live in one place and can be changed in one place.
:::

AAA ([Section 9.1](#s9-1){.ref}) is delivered by a central server, using one of two protocols. *RADIUS* is the standard for network access (users joining Wi-Fi, VPN or a switch port); *TACACS+* is preferred for administrators logging in to devices, because it can authorise each command.

| | RADIUS | TACACS+ |
|---|---|---|
| Transport | UDP 1812 (authentication), 1813 (accounting) | TCP 49 |
| AAA separation | authentication and authorisation combined | three separate functions |
| Encryption | password attribute only | whole packet body |
| Per-command authorisation | no (coarse privilege level) | yes (command sets) |
| Standard | open (RFC 2865) | originally Cisco-proprietary |
| Typical use | 802.1X, VPN, Wi-Fi | device administration |

For device administration, `aaa authentication login default group tacacs+ local` tries the server first and falls back to a local account only when the server is unreachable; `aaa authorization commands 15` and `aaa accounting commands 15` then check and record every privileged command. A strong local fallback account is essential, or an outage of the AAA server locks everyone out.

*IEEE 802.1X* controls access at the port. There are three roles: the *supplicant* (the laptop), the *authenticator* (the switch or access point), and the *authentication server* (a RADIUS server). Before authentication the port passes only EAPOL frames (EAP over LAN), like a college gate where the student shows an identity card to the guard, who telephones the administration office before opening. The switch does not interpret the credentials; it relays *EAP* messages in RADIUS packets (Figure 9.18). The EAP *method* decides what is proved. *EAP-TLS* uses certificates on both sides and is the strongest, but needs a certificate on every device. *PEAP* builds a TLS tunnel authenticated by the server's certificate and carries a password exchange (MSCHAPv2) inside it.

On success the RADIUS reply can include attributes that set the VLAN of the port (Tunnel-Type VLAN, Tunnel-Medium-Type 802 and Tunnel-Private-Group-ID), so that staff and students land in different VLANs on the same socket. Devices that cannot run a supplicant, such as printers, fall back to *MAC Authentication Bypass* (MAB), where the MAC address is the credential; it is weak, as MAC addresses are easily forged, so such devices go in a restricted VLAN. A policy server such as Cisco ISE adds *network access control*: it also checks device posture (patch level, antivirus) and may quarantine a non-compliant device.

## [9.13]{.sec}Detection and device hardening [Optional · ■□□]{.tag} {#s9-13}

::: bigidea
Prevention fails sometimes, so we add detection to learn of the failure, and we harden devices to make the failure less likely in the first place.
:::

An *intrusion detection system* (IDS) examines a copy of the traffic, taken from a SPAN port or an optical TAP, and raises alerts; an *intrusion prevention system* (IPS) sits inline and can drop or reset a flow (Figure 9.19). An IDS is like CCTV that alerts, an IPS is the guard who blocks. The price of blocking is risk: a false positive stops legitimate traffic, and an inline device that fails can cut the link unless it is set to fail open. *Signature-based* detection matches known patterns and has few false positives but misses novel attacks; *anomaly-based* detection flags deviations from a learned baseline and finds new attacks but raises more false alarms. Snort and Suricata are signature engines, and Zeek logs protocol behaviour for analysis. *NetFlow* and IPFIX records, which summarise flows without payload, reveal scans and exfiltration cheaply. A *SIEM* collects logs and flows from all sources and correlates them, for example "twenty failed logins, then a success, from a new country".

A signature is a rule. This Suricata rule alerts when one source opens ten SSH connections to the web server within a minute, and the alert it produces names the rule, the class and the flow.

```
alert tcp $EXTERNAL_NET any -> 10.0.0.80 22 (msg:"SSH brute force"; flow:to_server;
  threshold:type both, track by_src, count 10, seconds 60; classtype:attempted-admin; sid:1000001; rev:1;)
```

```
10/29/2026-14:02:11.512344  [**] [1:1000001:1] SSH brute force [**]
  [Classification: Attempted Administrator Privilege Gain] [Priority: 1] {TCP} 198.51.100.77:50122 -> 10.0.0.80:22
```

::: example
**Why false positives dominate.** Suppose 1 flow in 10,000 is an attack, and the sensor detects 99 % of attacks but wrongly flags 1 % of benign flows. In 1,000,000 flows there are 100 attacks, of which 99 are caught, and 999,900 benign flows, of which 9,999 are flagged. Of the 10,098 alerts only 99 are real, a precision of about 1 %.

[Result: because attacks are rare, even a 1 % false-positive rate buries the true alerts, so rules must be tuned and alerts correlated before anyone is paged.]{.result}
:::

*Device hardening* reduces the attack surface of the routers and switches themselves. The following diff shows an insecure Campus Net router and its hardened version, with the reason for each change.

```
! before
service password-encryption
enable password cisco
username admin password cisco
line vty 0 4
 transport input telnet
snmp-server community public RO
ip http server
```

```
! after
enable algorithm-type scrypt secret <pw>
username admin privilege 15 algorithm-type scrypt secret <pw>
crypto key generate rsa modulus 3072
ip ssh version 2
line vty 0 4
 transport input ssh
 access-class MGMT-ONLY in
 exec-timeout 5 0
snmp-server group MON v3 priv
no ip http server
ip http secure-server
logging host 10.0.0.30
ntp authenticate
interface range GigabitEthernet1/0/2 - 24
 no cdp enable
```

| Change | Reason |
|---|---|
| `scrypt` (type 9) or `sha256` (type 8) secrets | type 7 from `service password-encryption` is reversible in seconds and type 5 (MD5) is weak |
| SSH version 2 only, Telnet off | Telnet sends passwords in clear |
| `access-class` on VTY | only the management network may even attempt a login |
| SNMPv3 `priv` | v1 and v2c send the community string in clear; v3 authenticates and encrypts |
| HTTPS only | the HTTP server sends passwords in clear |
| Syslog and authenticated NTP | consistent timestamps and a record that an attacker cannot easily erase |
| CDP and LLDP off on user ports | they disclose model, software version and addresses |

Further measures: *control-plane policing* (CoPP) rate-limits traffic addressed to the router so that a flood cannot starve routing protocols; a *management VRF* keeps management traffic off the production routing table; unused services and ports are shut down.

::: trap
*Claim:* `service password-encryption` protects the configuration's passwords. *Why it is wrong:* it applies the reversible type-7 obfuscation, which any tool decodes immediately. *Correct statement:* use `secret` commands with type 8 or 9 hashing and keep configuration files access-controlled.
:::

## [9.14]{.sec}Zero trust [Should · ■■□]{.tag} {#s9-14}

::: bigidea
Zero trust removes the assumption that a request from "inside" the network is safe, because attackers who get one foothold would otherwise move freely, so every request is decided on identity, device and context.
:::

The classical design is a castle with a moat: a hard perimeter (firewall, VPN) and trust inside it. Its weakness is that one stolen laptop or phished password gives an intruder the whole interior. *Zero trust* (NIST SP 800-207) treats the network as hostile everywhere. Instead of one gate to the IT park, every office door has a badge reader that checks who you are and whether your laptop is patched, each time. Its seven tenets are listed in the Revision Spread.

The architecture has three logical parts (Figure 9.20). The *Policy Enforcement Point* (PEP) sits in front of each resource and opens or closes the session. The *Policy Decision Point* is made of a *Policy Engine*, which computes the decision from the inputs, and a *Policy Administrator*, which tells the PEP and sets up the session. The inputs include the identity provider, device posture and compliance data, threat intelligence, activity logs, and the policy store itself. Decisions are made per request, not once per login.

| | Perimeter model | Zero trust |
|---|---|---|
| Trust granted by | network location | identity, device state and context |
| Access given | to the network segment | to one application, per session |
| Lateral movement | easy once inside | limited by micro-segmentation |
| Remote user | full VPN | identity-aware proxy |
| Example | firewall plus VPN | Google BeyondCorp |

*Micro-segmentation* applies the same idea inside data centres: workloads may talk only on explicitly permitted flows, enforced by host firewalls or a service mesh using mutual TLS. *SASE* and *SSE* are names for cloud services that deliver the PEP, secure web gateway and related functions to remote users; we need only the names.

::: example
**A contractor needs one internal wiki.** The VPN design gives the contractor's laptop an address on the staff network, from where every server is reachable. The zero-trust design publishes the wiki through an identity-aware proxy.

1. The contractor signs in at the proxy with the identity provider and multi-factor authentication.
2. The proxy (the PEP) asks the decision point. Inputs: the contractor's group, "contractor"; the device certificate and patch status; the time and location; the resource, "wiki"; the threat score of the session.
3. If all conditions hold, the proxy opens a session to the wiki only, for a limited time. Every request is checked again, and every decision is logged.
4. If the laptop's patch level changes, the next request is refused without any change to the network.

[Result: access follows the person and the device to one application, not the address to a segment.]{.result}
:::

Migration from a VPN is gradual: inventory applications and identities first, put identity and device inventory under central control, publish the least critical application through the proxy, then move others, and retire the broad VPN last. The migration is mapped to the NIST components in Q9.30.
