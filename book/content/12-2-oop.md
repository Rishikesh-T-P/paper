## [12.8]{.sec}Object-oriented programming for the viva [Must · ■■□]{.tag} {#s12-8}

Object-oriented programming, or OOP, organises a program as objects that bundle data with the functions that act on it. Panels ask about it because the vocabulary is short and answers reveal at once whether a candidate has written a program of any size. The C++ mechanics live in [§2.19](#s2-19){.ref} and [§2.20](#s2-20){.ref}; this section supplies the viva-ready answers and uses Python for code, because network-automation libraries are written in it ([Pillar 10](#ch10){.ref}).

::: bigidea
Every OOP term answers one question: how do we change one part of a program without breaking the rest?
:::

### The four pillars with a networking example

| Pillar | One-line meaning | Network example | Mechanism to quote |
|---|---|---|---|
| Encapsulation | Data and the code that guards it live together; outsiders use a controlled interface | `Interface.set_mtu()` rejects values outside 68 to 9,216 | Access specifiers (`private`, `protected`, `public`); `_name` convention in Python |
| Abstraction | Expose what an object does, hide how | `device.get_config()` without knowing the vendor command | Abstract classes and interfaces |
| Inheritance | A new class reuses and extends an existing one ("is-a") | `CiscoIOS` and `JunosDevice` extend `Device` | `class B : public A`; `class B(A)` |
| Polymorphism | One call, different behaviour by the object's real type | `for d in devices: d.get_config()` | Virtual functions (run time); overloading (compile time) |

Encapsulation and abstraction are often confused. Encapsulation is about *protecting* state by bundling and access control; abstraction is about *simplifying* by showing only essentials. A TV remote is the usual analogy: the buttons are the abstraction, and the sealed circuit board is the encapsulation.

### Classes, objects, constructors

A *class* is a blueprint that fixes the data members and member functions; an *object* is one instance of it with its own values. A *constructor* runs when the object is created, to establish a valid state; a *destructor* runs when it is destroyed. In C++ constructors run base first, then derived, and destructors run in the reverse order. A class that is meant to be inherited must declare its destructor `virtual`, because otherwise deleting a derived object through a base pointer skips the derived destructor.

[**Shallow copy** — copies pointer values, so two objects share one block; the second `delete` is a double free. A **deep copy** duplicates the block. Rule of three: if you write one of destructor, copy constructor or copy assignment, write all three.]{.margin}

### Overloading, overriding and hiding

| | Overloading | Overriding |
|---|---|---|
| Meaning | Same name, different parameter lists | Derived class replaces a base-class function with the same signature |
| Binding | Compile time (static) | Run time (dynamic), if the base function is `virtual` |
| Scope | Within one class | Across a base and a derived class |
| Return type | May differ (but not alone) | Must match, or be covariant |
| Python | Not supported; the last definition wins; use default arguments or `functools.singledispatch` | By defining the method again |

::: trap
*Claim:* "Polymorphism means many forms," and nothing more. *Why it is wrong:* it names the idea and omits the mechanism, so the examiner learns nothing. *Correct statement:* in C++, a call through a base pointer to a `virtual` function is resolved at run time through the object's *vptr*, which points to the *vtable* of its real class; overloading is resolved by the compiler from the argument types.
:::

### Abstract classes and interfaces

| | Abstract class | Interface |
|---|---|---|
| Can hold data and implemented methods | Yes | Java and C#: default methods only, no instance state |
| Instantiable | No | No |
| A class may extend | One (Java), several (C++, Python) | Many |
| C++ | At least one pure virtual function (`= 0`) | No keyword: an abstract class with only pure virtuals |
| Python | Subclass of `abc.ABC` with `@abstractmethod` | Same, or a `typing.Protocol` |
| Use when | Related classes share code and a contract | Unrelated classes share only a contract |

### How virtual dispatch works

Each class with virtual functions has one *vtable*, an array of function pointers; each object stores one hidden pointer, the *vptr*, to its class's table. A virtual call loads the vptr, indexes the table and jumps. The cost is one pointer per object (8 bytes on a 64-bit machine), one extra memory read per call, and the loss of inlining. [§2.20](#s2-20){.ref} shows the layout with `sizeof` output.

### SOLID in brief

| Letter | Principle | Violation | Repair |
|---|---|---|---|
| S | Single responsibility: one reason to change | A `Router` class that also parses configs and sends e-mail | Split into `Router`, `ConfigParser`, `Notifier` |
| O | Open for extension, closed for modification | An `if vendor == ...` chain edited for every new vendor | A new subclass; no existing code changes |
| L | Liskov substitution: a subclass must work wherever its base does | `ReadOnlyDevice` raises an error in `set_config()` | Separate readable and writable interfaces |
| I | Interface segregation: no client forced to depend on methods it does not use | One `Device` interface with `bgp_neighbours()` that a switch cannot implement | Small interfaces: `Routing`, `Switching` |
| D | Dependency inversion: depend on abstractions, not concrete classes | A monitor that constructs `CiscoIOS` itself | The monitor receives a `Device`; a factory supplies it |

### Five patterns in one table

| Pattern | Intent | Network example | Cost or caution |
|---|---|---|---|
| Singleton | One instance, global access | A logger or connection pool | Hidden global state makes tests hard |
| Factory | Create objects by a key without naming the class | `ConnectHandler(device_type="cisco_ios")` in Netmiko | One more indirection |
| Strategy | Swap an algorithm at run time | Pluggable route-metric calculators | Many small classes |
| Observer | Notify subscribers when state changes | Telemetry consumers subscribed to interface counters | Order and failure of callbacks |
| Adapter | Wrap an incompatible interface | A common API over vendor REST and CLI | The wrapper can leak vendor detail |

::: example
**Replace an `if vendor == ...` chain with a factory that follows the open-closed principle.**

1. Define the contract once as an abstract class; each vendor supplies only what differs.
2. Register the classes in a dictionary keyed by vendor name.
3. The caller asks the factory and never names a vendor class.

```python
from abc import ABC, abstractmethod

class Device(ABC):
    def __init__(self, host): self.host = host
    @abstractmethod
    def show_config_cmd(self): ...
    def get_config(self):
        return f"{self.host}: {self.show_config_cmd()}"

class CiscoIOS(Device):
    def show_config_cmd(self): return "show running-config"
class Junos(Device):
    def show_config_cmd(self): return "show configuration"

DRIVERS = {"ios": CiscoIOS, "junos": Junos}
def connect(kind, host): return DRIVERS[kind](host)

print(connect("junos", "r1").get_config())   # r1: show configuration
```

[Result: adding EOS means one new class and one dictionary entry; `Device("x")` raises `TypeError`, because it is abstract. This is the same shape as NAPALM's drivers ([§10.7](#s10-7){.ref}).]{.result}
:::

### Questions that recur as MCQs

| Question | Answer |
|---|---|
| Can a constructor be virtual? | No: the vptr is not yet set when it runs |
| Can a destructor be virtual? | Yes, and it must be in a polymorphic base class |
| Which function is called on a base pointer to a derived object without `virtual`? | The base version (static binding) |
| What is the diamond problem? | A class inherits one base through two paths; C++ uses `virtual` inheritance, and Python resolves it by the C3 method resolution order |
| Can an abstract class have a constructor? | Yes; it runs when a derived object is built |
| `static` member function | Belongs to the class, has no `this`, cannot be virtual |
| Composition or inheritance? | Prefer composition ("has-a") unless the relationship is truly "is-a" |
